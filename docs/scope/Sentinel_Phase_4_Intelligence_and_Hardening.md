# Sentinel — Phase 4: Evidence-Grounded Intelligence and Hardening

**Companion to:** Sentinel PRD v1 and Phases 1–3 guides  
**Learning block:** AI engineering (curriculum Month 5) and AppSec/integration (Month 6)  
**Entry condition:** A reliable deployed evidence pipeline and representative incident fixtures  
**Date:** 8 November 2026

## 1. Outcome

Sentinel helps engineers investigate an incident with structured, evidence-linked AI findings while clearly communicating uncertainty. The system can retrieve relevant prior incidents and runbooks, suggest hypotheses and next checks, and let a human inspect every supporting source before acting. Its tenant, connector, prompt and tool boundaries have been threat-modeled and tested. Unsupported claims and adversarial inputs are part of the evaluation suite.

AI is an interpretation layer over the evidence pipeline built in earlier phases. It does not become the source of truth, quietly invent telemetry, or execute production remediation.

## 2. Product behavior

Given an incident, the investigator receives a bounded, tenant-scoped evidence bundle: alert, component and dependency map, time-ordered log/metric summaries, deployments, retrieval statuses and selected historical context. It returns:

1. **Observed facts** with evidence IDs and source links.
2. **Candidate explanations** with the supporting and contradicting evidence, plus explicit limitations.
3. **Unknowns and missing sources** that affect confidence.
4. **Prioritized next checks** that an engineer can perform.
5. **Optional related incidents/runbooks** with reason for retrieval.

No output field called `confirmed_root_cause` is generated by the model. A human can record the final cause separately. Multiple recent deployments remain distinct candidates unless evidence differentiates them.

## 3. Learning application

| AI/AppSec topic | Sentinel exercise |
| --- | --- |
| Structured model outputs | Validate a typed finding schema; reject malformed or uncited factual claims |
| Retrieval/RAG | Compare prior incidents and runbooks with and without retrieval on held-out cases |
| Tool use | Give the investigator narrow read-only tools with tenant and query budgets |
| Evaluation | Measure evidence support, usefulness, abstention and retrieval quality on scripted incidents |

The curriculum mentions agents and vector search. Adopt either only if it beats a simpler retrieval or orchestrated pipeline on the evaluation set.

## 4. Evidence preparation and retrieval

### 4.1 Evidence bundle

Create a versioned input snapshot for each analysis revision. It includes incident ID, organization/project/component scope, query time window, normalized evidence IDs, source status, retrieval timestamps and content hashes where appropriate. Keep raw untrusted source text separate from instructions and metadata. Include provenance even when a source is unavailable.

Limit amount of log text and history submitted to a model. Redact credentials and personal data before model use; decide where data is processed and retained before enabling real customer data. An analysis revision records the evidence snapshot and model/prompt configuration used to produce it so an engineer can reproduce or audit the result.

### 4.2 Historical context

First add keyword/metadata retrieval over resolved incidents and curated runbooks, scoped to the same organization. Use component, environment, symptoms and time filters. Define a small relevance test set. Add embeddings/vector retrieval only if it improves useful recall or handles wording differences that simpler search misses. Include “no related case found” when retrieval is empty.

### 4.3 Tools

If using tool calling, permit narrow read-only operations: get a permitted incident, query a bounded source window, retrieve runbook excerpt, inspect deployment metadata. Each tool enforces organization, project, component, time/query budgets and audit logs independently of the model's stated intent. Block arbitrary shell commands, network fetches, credential reads, write APIs and remediation tools.

## 5. Investigator pipeline

| Stage | Contract | Failure behavior |
| --- | --- | --- |
| Select evidence | Use persisted incident and connector results with source status | Report gaps; do not fill them from imagination |
| Retrieve history | Tenant-scoped search of prior incidents/runbooks | Continue without history and mark unavailable |
| Generate findings | Typed observations, hypotheses, unknowns and next checks | Retry boundedly or fall back to deterministic Phase 1/2 analysis |
| Validate | Check schema, evidence IDs, tenant scope and unsupported references | Reject or mark invalid claims; no uncited factual statement reaches the UI |
| Present | Show sources, uncertainty, revision and human feedback controls | Human can inspect original evidence and disagree |

An evidence citation is necessary but not sufficient: the cited item must actually support the claim. The evaluation process samples this semantic correctness. Avoid a single numeric confidence score without calibration; use clear language about what supports or weakens a hypothesis.

## 6. Evaluation plan

Build a held-out set of at least several representative incident cases before tuning prompts. The set should include:

- Simple deployment followed by matching failures.
- Several deployments in a short window with no clear culprit.
- Provider outage causing application errors without a local code change.
- Alert with no logs or metrics.
- Contradictory signals: error rate high while one service's health metric looks normal.
- Late/out-of-order events and a failed connector.
- A resolved historical incident that is genuinely analogous, and one that only shares keywords.
- Malicious log/runbook text asking the model to ignore instructions or expose secrets.
- A cross-tenant retrieval attempt.

For each case, write an evidence inventory and expected *allowable* findings rather than one exact prose answer. Review with a rubric: factual support, missing-data honesty, correct component scope, next-step usefulness, retrieval relevance, absence of unsafe actions, latency and cost. Compare deterministic baseline, model without retrieval and model with retrieval. Record failure examples and changes to prompts/retrieval. Keep a human adjudication sample; automated checks alone cannot verify causal reasoning.

## 7. Security threat model

| Boundary | Threat | Test and control |
| --- | --- | --- |
| Human API → tenant data | IDOR/BOLA, privilege escalation | Cross-tenant project/incident IDs and role tests; scope every query |
| Webhook → intake | Spoofing, replay, oversized or malicious payload | Signature/token verification, source ID deduplication, size limits, rate limits |
| Connector → remote endpoint | SSRF, redirect/DNS tricks, token theft | Allowlisted destinations/network policy, redirect limits, least-privilege read tokens |
| Logs/runbooks → model | Prompt injection and secret exfiltration instructions | Treat content as data, validate tools server-side, redaction and adversarial tests |
| Model → UI | Fabricated citations or unsafe advice | Schema/evidence validation, source inspection and human control |
| CI/CD → deployment | Secret leaks, vulnerable dependencies/images, excessive permissions | Secret scanning, dependency/container/IaC checks and scoped credentials |

Use practical AppSec exercises against Sentinel, including auth and object authorization, SQL injection, SSRF, race conditions in incident grouping, integration permissions and malicious content. Record each finding, impact, reproduction, remediation and regression test. A security scanner's green result is not a substitute for tenant and business-logic tests.

## 8. Privacy and governance

- Document which evidence leaves the customer's telemetry system, how long it stays in Sentinel, which model provider processes it and what is stored in prompts/traces.
- Enforce organization retention and deletion rules for events, snippets, embeddings and analysis revisions. Deletion should cover derived retrieval indexes where relevant.
- Encrypt upstream secrets and restrict the investigator to read-only source access. Audit connector usage and model tool calls by incident and tenant.
- Redact credentials, payment data and personal identifiers from logs and model input. Test redaction with fixtures; preserve enough context for useful debugging without retaining raw secrets.
- Disclose analysis limitations in the UI and let an engineer correct or dismiss a finding. Never automatically execute a proposed fix.

## 9. Work packages and sequence

| Package | Build | Gate |
| --- | --- | --- |
| **P4-A: evaluation cases** | Held-out incident fixtures, evidence inventories and scoring rubric | Baseline results and failure cases recorded before model tuning |
| **P4-B: retrieval** | Tenant-scoped prior-incident/runbook search and provenance | Relevant case surfaces; irrelevant keyword match is rejected |
| **P4-C: AI analysis** | Structured output, bounded orchestration, citation validation, fallback | Useful findings cite supporting evidence; missing evidence produces abstention |
| **P4-D: feedback and cost** | Human verdicts, revision audit trail, latency/token/cost metrics | An engineer can inspect, reject and compare revisions |
| **P4-E: threat model and tests** | Tenant, webhook, connector, log/prompt and CI/CD attack exercises | High-impact findings fixed with regression tests |
| **P4-F: capstone review** | Architecture, scaling/cost analysis, runbooks, demo and portfolio narrative | End-to-end incident exercise is reproducible and limitations are explicit |

Do not wait until all AI techniques are studied to ship a first cited summary. Add one capability, evaluate it, and keep it only if it improves the investigation.

## 10. Acceptance scenarios

1. An incident with supporting logs, metric change and deployment evidence yields observations and candidate explanations that link to actual source items.
2. Two recent deployments are both considered; the model does not claim the latest commit caused the error without discriminating evidence.
3. Missing or failed sources are shown as gaps; the analysis can say “unknown” and suggests a bounded next check.
4. A malicious log line or runbook cannot change tenant scope, invoke a forbidden tool or expose a secret.
5. A finding citing a nonexistent or irrelevant evidence ID is rejected or visibly flagged before presentation.
6. Retrieval cannot return another organization's incident even if its text is a close semantic match.
7. Model outage or invalid output leaves deterministic analysis and incident timeline available.
8. Investigation cost, latency, prompt/model version and evidence snapshot can be inspected for a revision.
9. An engineer can mark a finding incorrect, inspect sources and record the eventual human conclusion.
10. Security review covers tenant isolation, connector URLs and credentials, event spoofing, prompt injection and supply-chain controls with documented remediations.

## 11. Exit package

Deliver the evaluation dataset and rubric, retrieval decision record, prompt/schema versions, evidence validation tests, model/cost dashboard, threat model, findings and remediations, regression suite, final architecture diagram, operational runbooks and a reproducible end-to-end demo. The capstone README explains what Sentinel does, what it does not know, why each infrastructure choice was made, and where an engineer remains in control.

The product can continue after this phase with more integrations, similar-incident retrieval and assisted runbooks. Each addition must improve the core loop and demonstrate value on realistic incidents.
